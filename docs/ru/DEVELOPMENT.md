# Руководство разработчика TTS Enhancer

> Практическое руководство для контрибьюторов и сопровождающих плагина.
> Сопутствующие документы: [Архитектура](ARCHITECTURE.md) · [Известные ограничения и ответственность вышестоящих компонентов](KNOWN_LIMITATIONS.md) · [English README](../en/README.md) · [CHANGELOG](../../CHANGELOG.md)

В этой статье «как добавить нового TTS-провайдера» служит основной нитью, связывающей адаптеры, документы о возможностях, конфигурацию, фронтенд, тестирование и все остальные этапы.

## 1. Подготовка окружения

### 1.1 Окружение для запуска / отладки

- Python ≥ 3.10 (та же версия, что и у AstrBot).
- В дереве исходников AstrBot создайте символическую ссылку или скопируйте каталог плагина в `data/plugins/astrbot_plugin_tts_enhancer/`, запустите AstrBot и включите плагин в WebUI.
- Бэкенд-зависимости (асинхронный HTTP и т.д.) предоставляются основным окружением AstrBot; если адаптеру нужны дополнительные библиотеки, добавьте их в `requirements.txt` в корне плагина (AstrBot их установит).

### 1.2 Окружение для тестов (pytest)

- Набор тестов находится в `tests/`, в `pytest.ini` уже задано `asyncio_mode = auto`.
- `requirements-tests.txt` объявляет `pytest` и `pytest-asyncio`, изолируя зависимости от основного окружения.
- `tests/conftest.py` **ищет корень исходников AstrBot вверх по дереву** (больше нет жёстко заданного уровня вложенности) и использует `pytest.importorskip("astrbot.core.provider")` — вне дерева AstrBot тесты корректно пропускаются, а не падают.

```bash
# в корне плагина
pip install -r requirements-tests.txt
pytest                # запуск внутри дерева исходников AstrBot
```

### 1.3 Фронтенд (без сборки)

- Фронтенд — нативные ES Module + локальный Vue UMD, **этап сборки отсутствует**, изменения в JS вступают в силу сразу.
- У фронтенда нет `package.json` или конфигурации ESLint, поэтому шаг инструментария `npm install` / `npx eslint` не требуется.

## 3. Добавление нового TTS-провайдера (чек-лист)

| Шаг | Результат | Обязательно? |
|-----|-----------|--------------|
| 1. Написать адаптер | `providers/<template_key>.py` | ✅ |
| 2. Написать документ о возможностях | `providers/docs/<docs_key>.md` (может включать `_design.md`) | ✅ (иначе откат на обычный текст) |
| 3. Схема конфигурации | новый шаблон в `providers.templates` файла `_conf_schema.json` | ✅ |
| 4. Интеграция во фронтенд | `pages/tts_studio/components/*.js` + регистрация в `app.js` | только если нужен UI |
| 5. Тесты | новые тесты в `tests/` | настоятельно рекомендуется |

> Все новые провайдеры **автоматически обнаруживаются и загружаются** фабрикой `ProviderFactory` — изменение кода ядра не требуется. Имя файла (без `.py`) — это `template_key`, который должен совпадать с ключом `templates` в `_conf_schema.json`.

## 4. Разработка адаптера подробно

### 4.1 Минимальный рабочий адаптер

```python
"""Пример адаптера TTS"""

from .base import TTSProviderAdapter


class ExampleTtsAdapter(TTSProviderAdapter):
    """Адаптер примера провайдера"""

    def get_subagent_system_prompt(self) -> str:
        docs = self.docs_content
        return (
            f"Вы — помощник по оптимизации параметров синтеза речи. Описание параметров:\n\n{docs}\n\n"
            "Вызовите инструмент tts_enhance напрямую, без дополнительных объяснений."
        )

    def get_tool_schema(self):
        # через базовый build_enhance_tool создаём tts_enhance и автоматически подключаем обработчик проверки
        # (см. base.py: фиксированное имя инструмента, единая конструкция FunctionTool и подключение _handle_enhance_tool)
        return self.build_enhance_tool(
            description="Параметры, необходимые для синтеза текста в речь",
            parameters={...},  # схема параметров этого адаптера
        )

    async def call_api(self, text, raw_params, config, voice_id=None) -> str:
        # 1. объединить конфигурацию и raw_params (параметры инструмента имеют приоритет)
        # 2. сформировать запрос, вызвать API, загрузить аудио
        # 3. сохранить на диск и вернуть путь; при неудаче вернуть "" (не пробрасывать неперехваченное исключение в основной поток)
        ...
```

### 4.2 Обязательные абстрактные методы

- `get_subagent_system_prompt() -> str`: присоединяет документ о возможностях и направляет SubAgent на генерацию параметров.
- `get_tool_schema() -> FunctionTool | None`: через базовый `build_enhance_tool` возвращает инструмент `tts_enhance` (с уже подключённым обработчиком проверки). Возврат `None` означает отсутствие поддержки Function Calling (будет откат на обычный текст).
- `call_api(text, raw_params, config, voice_id=None) -> str`: ядро синтеза. Возвращает путь к аудиофайлу; **при неудаче возвращает пустую строку**, а не выбрасывает исключение (основной поток по ней переключает провайдера). `voice_id` используется для явного переопределения голоса при превью.

### 4.3 Опциональные возможности (управление голосами / файлами)

По умолчанию `raise NotImplementedError`, маршрут в `main.py` перехватывает это и возвращает `501`. После реализации методы вызываются фронтендом/маршрутами:

- Голоса: `create_voice(params)`, `list_voice(**kwargs)`, `delete_voice(**kwargs)`.
- Файлы: `upload_file(file_path, **kwargs)`, `list_files(**kwargs)`, `get_file_content(file_id)`, `delete_file(file_id, **kwargs)`.

> Маршруты управления файлами (`/file/*`) передают все параметры, кроме `entry_id`/`file_id`, адаптеру как `**kwargs`, сохраняя гибкость расширения.

### 4.4 Проверка и очистка параметров

- **Проверка диапазонов/перечислений**: переопределите `validate_params(params) -> (bool, str)`. При возврате `(False, msg)` SubAgent отправляет LLM структурированный результат инструмента с `role:"tool"` (включая текст ошибки) для повторной попытки; при последней неудаче — очистка через `sanitize_params`.
- **Очистка**: переопределите `sanitize_params(params) -> dict`, отбрасывая некорректные и сохраняя корректные значения (например, числа, возвращённые LLM как строки, нормализуются через `_as_float`/`_as_int` с исключением `bool`).
- **Общая проверка**: используйте унаследованные `validate_voice_id()`, `validate_text_length()` (иероглиф = 2 символа, согласовано с фронтенд `useTextValidator`), чтобы не дублировать реализацию.
- **Безопасность типов**: разбор параметров всегда через `_as_float` / `_as_int`, чтобы не «отвергать строковые числа» и не «пропускать bool».

### 4.5 Соглашение по сохранению аудио на диск

- Результаты синтеза сохраняются через `save_audio_bytes(data_dir, content, fmt)` из `providers/utils/audio.py` — функция сохраняет в `config["_data_dir"]` с именем по метке времени и возвращает путь.
- `_data_dir` внедряется в словарь entry через `TTSService`/`main.py` (значение — `plugin_data/<name>/audio`), адаптер **не должен жёстко задавать путь**.

### 4.6 Переиспользование utils

- `providers/utils/http.py`: `bearer_headers(api_key, with_json=True)`, `extract_error_message(payload, fallback_text)` (совместимо с `message`/`error`/`detail`).
- `providers/utils/audio.py`: `save_audio_bytes(...)`, `get_audio_duration`, `validate_audio_duration`, `trim_audio_to_max`, `AudioConstraints` (константы ограничений длительности для платформ).

### 4.7 Соглашение по переопределению `voice_id`

Параметр `voice_id` в `call_api` предназначен для «явного переопределения голоса при превью». Стандартная запись:

```python
voice = voice_id or config.get("voice") or config.get("voice_id")
if not voice:
    raise ValueError("Не указан ID голоса, синтез речи невозможен")
```

Имена ключей конфигурации у провайдеров сохраняются в соответствии с вышестоящим API (у Bailian `voice`, у MiniMax `voice_id`), unification не навязывается.

## 5. Правила написания документов о возможностях

Файл: `providers/docs/<docs_key>.md`, читается SubAgent напрямую и внедряется. Рекомендуемая структура:

1. **Обзор**: источник и позиционирование модели.
2. **Таблица ключевых параметров**: обязательные/опциональные параметры (тип, диапазон, значение по умолчанию, описание).
3. **Перечисления**: языки, теги эмоций, диалекты и т.д.
4. **Примеры использования**: с полным примером параметров `tts_enhance`.
5. **`## 你的任务` (ключевой раздел)**: явно сообщить SubAgent, как выбирать параметры по контексту и когда вызывать `tts_enhance`.
   - Например: «В соответствии с интонацией контекста добавляйте управляющие теги в text; управляйте деталями через instruction/rate/volume; вызывайте tts_enhance напрямую».

Если определённый тип голоса (например, дизайн-голос) имеет ограниченные возможности (не поддерживает диалекты), опишите его отдельно в `<docs_key>_design.md` и переключайтесь автоматически по ID голоса через `get_docs_for_voice(voice)` в адаптере; для одной модели можно задать `DOCS_KEY` в подклассе для переиспользования документа.

## 6. Расширение схемы конфигурации

В `providers.templates` файла `_conf_schema.json` добавьте шаблон с ключом `template_key`:

```json
"my_provider": {
  "name": "Мой провайдер",
  "hint": "Краткое описание возможностей",
  "display_item": "display_name",
  "items": {
    "display_name": { "description": "Отображаемое имя", "type": "string", "default": "Мой провайдер" },
    "priority":     { "description": "Приоритет (меньше — выше)", "type": "int", "default": 0 },
    "persona_id":   { "description": "Привязка к персоне", "type": "string", "_special": "select_persona", "default": "" },
    "api_key":      { "description": "API Key", "type": "string", "secret": true },
    "model":        { "description": "Модель", "type": "string", "options": ["a", "b"], "default": "a" }
  }
}
```

Основные моменты:

- `_special: select_provider` / `select_persona`: отображается как выпадающий список.
- `secret: true`: маска поля пароля.
- `options`: фиксированный список для выпадающего выбора; `condition`: условное отображение по значениям других полей (например, MiMo переключает поля голоса/дизайна/клонирования по `model`).
- Фреймворк автоматически внедряет `__template_key` и отображаемое имя, заданное через `display_item`.

## 7. Интеграция во фронтенд

### 7.1 Когда нужен фронтенд

- **Уже есть официальная консоль**: достаточно добавить отображаемое имя в `getDisplayName` файла `app.js` и настроить внешнюю ссылку в `providerConfig` — **писать компонент не нужно**.
- **Есть только API**: напишите компонент в `components/`, переиспользуйте общие компоненты из `components/common/` и зарегистрируйте его в `componentMap` файла `app.js`.

### 7.2 Регистрация компонента (`app.js`)

```js
import MyProvider from './components/my_provider.js';
// добавить в componentMap: 'my_provider': MyProvider
// добавить в getDisplayName: 'my_provider': 'Мой провайдер'
```

### 7.3 providerConfig и общие компоненты

Провайдеры семейства Bailian напрямую переиспользуют `components/common/bailian_speech_synthesizer.js`; тонкая обёртка объявляет только отличия:

```js
export default {
  components: { BailianSpeechSynthesizer },
  // providerConfig: { displayName, supportedLanguages, supportsSystemVoices, systemVoiceLinks, designHelpLink }
};
```

Общий компонент инкапсулирует режимы клонирования/дизайна (аудио клонирования кодируется в браузере как Data URL и отправляется напрямую), прослушивание, список, удаление, а также `voice_preview_modal` / `delete_confirm_modal` (замена `confirm()` в песочницах).

### 7.4 bridge API

Все вызовы бэкенда идут через `window.AstrBotPluginPage` (`bridge`):

- `await bridge.ready()`: убедиться, что bridge готов.
- `await bridge.apiGet('providers')`: получить сгруппированный список провайдеров.
- `bridge.upload(...)`: загрузка файлов (обходит аутентификацию `asset_token` и кросс-доменные ограничения).
- Остальные маршруты вызываются как `bridge.apiPost('<route>', payload)` (например, `voice/create`, `file/upload`, `kv/set` и т.д.).

### 7.5 composables

- `useAudioManager`: синглтон глобального воспроизведения аудио (общая громкость, переключение между компонентами).
- `useTextValidator`: `countChars` (иероглиф = 2), `validateText({label,min,max,required})` → `{valid,error,count}`.
- `useClipboard`, `useToast`: буфер обмена и уведомления.

### 7.6 Соглашения по наложениям и анимациям

- **Модальные окна / Toast всегда телепортируются в body**: `<Teleport to="body"><Transition name="modal"><div class="modal-overlay">…`. После завершения анимации появления страницы (`animation-fill-mode: both`) Chrome оставляет на родителе два типа побочных эффекта — единичную матрицу преобразования (становящуюся содержащим блоком для fixed-потомков и привязывающую наложение к боксу анимированного предка) и compositor-слой (т.е. контекст наложения, жёстко фиксирующий z-index поддерева); Teleport в body — единственное надёжное решение. Размер оверлея задавайте `100vw/100vh`, а не `100%` (классическая проблема со скроллбаром).
- **Для появления/исчезновения используйте `<Transition>`, а не CSS animation**: классы enter/leave у Transition снимаются сразу после проигрывания, элемент возвращается в обычное состояние; `animation-fill-mode: both` навсегда оставляет на элементе преобразвание / compositor-слой (источник двух описанных выше побочных эффектов).
- **Для непрерывных переходов используйте transform**: например, полоса подсветки вкладки — `translateX + scaleX` + `will-change`, рендер через compositor без покадровой вёрстки в основном потоке.
- **reduced-motion**: все анимации отключаются через `transition/animation: none` внутри `@media (prefers-reduced-motion: reduce)`.
- **Атрибуты темы / CSS-переменные можно вешать только на `html` / `body`, но не на `#app`**: телепортированные наложения (полоса громкости, все модалки, toast) уже вне поддерева `#app` и могут наследовать только определения уровня `:root` / `html`. Сейчас переменные темы находятся в `:root`, наложения в безопасности; однако это **неявный контракт** — если в будущем перенести атрибуты или переменные темы на `#app`, все наложения молча потеряют тему без какой-либо ошибки.

## 8. Правила тестирования

### 8.1 Запуск тестов

```bash
pip install -r requirements-tests.txt
pytest                 # внутри дерева исходников AstrBot
pytest tests/test_xxx.py -k "case"   # один файл / один тестовый случай
```

### 8.2 Соглашения conftest

- Автоматически определяет корень исходников AstrBot, `importorskip` пропускает тесты при отсутствии зависимостей.
- Предоставляет фикстуры для удобного создания `entry`, моков Provider и т.д. (подробнее — `tests/conftest.py`).

### 8.3 Соглашение xfail (важно)

- Известные дефекты / компромиссы дизайна / гарантии вышестоящих компонентов / недостижимые пути **фиксируются через `@pytest.mark.xfail`** как сигнал для регрессии, а не оформляются обычными тестами «на закрепление текущего положения», блокирующими будущие исправления.
- После исправления соответствующего дефекта превратите xfail в обычный регрессионный тест.
- Написав новый тест, **откатите изменение и убедитесь, что тест падает**, чтобы избежать ложноположительных тестов.
- **После проверки** (продолжение временной стадии «зафиксировать через xfail» выше): если наблюдение по итогам второго review признано «не подлежащим исправлению», **не оставляйте xfail надолго** — обработайте его по характеру и занесите в `docs/zh/KNOWN_LIMITATIONS.md`:
  - компромисс дизайна → превратите в обычный зелёный тест, asserting «принятое поведение» (уберите из названия намёк на дефект `should_not`), зафиксировав текущий контракт.
  - гарантия вышестоящего / недостижимое → **оставьте как зелёный тест-страж** (по-прежнему фиксирует текущее поведение и сохраняет регрессионный датчик, не удаляйте); если аргумент «недостижимости» может перестать быть справедливым после рефакторинга (как в #14), добавьте минимальное укрепление кодом в одну строку.

## 9. Стиль кода и комментарии

- Комментарии и логи по умолчанию **на китайском** (сторонний личный плагин; английский используется только при PR в основной репозиторий AstrBot).
- Docstring следуют **стилю Google** (`Args`/`Returns`/`Raises`), подробнее — в существующих модулях.
- Для логирования единообразно `from astrbot.api import logger`, встроенный `logging` использовать запрещено.
- Следуйте KISS: избегайте ненужных абстракций и helper-функций; логику, которую можно встроить, не выносите в отдельную функцию.
- Для работы с путями используйте `pathlib.Path`, а не конкатенацию строк.

## 10. Релиз и версионирование

1. **Изменения в коде** → 2. **номер версии** (`version` в `metadata.yaml`, формат `vX.Y.Z`) → 3. **обновление README/CHANGELOG** → 4. **ветка + коммит** → 5. **push** (личный аккаунт GitHub, PAT).
2. `CHANGELOG.md` следует [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) и семантическому версионированию.
3. Многоэтапные задачи завершайте «проверкой wrap-up + записью в CHANGELOG».

## 11. Частые ловушки

- **Не сохраняйте данные в каталоге самого плагина**: пишите в `plugin_data/`, иначе данные потеряются при обновлении/переустановке.
- **`call_api` при неудаче возвращает пустую строку, а не исключение**: основной поток опирается на пустую строку для переключения провайдера.
- **Для разбора параметров используйте `_as_float/_as_int`**: LLM часто возвращает числа строками, и нужно исключить `bool`.
- **`template_key`, ключ шаблона в `_conf_schema.json` и имя файла адаптера должны совпадать**.
- **Отсутствие документа о возможностях → провайдер автоматически откатывается на обычный текст** (без ошибки, но с потерей улучшения).
