# Известные ограничения и ответственность вышестоящих компонентов

В этом файле собраны поведения, которые по итогам проверки отнесены к «компромиссу дизайна / гарантии вышестоящего компонента / недостижимому» и больше не исправляются этим плагином самостоятельно (или требуют лишь минимального укрепления кода).

Соответствующие тесты изначально фиксировались через `@pytest.mark.xfail(strict=True)`, а после второго review обработаны по характеру:

- **Компромисс дизайна**: превращены в обычные зелёные тесты, утверждающие «фактически принятое поведение» (из названия убран намёк на дефект `should_not`),
  чтобы зафиксировать текущий контракт, не допускать постоянного вводящего в заблуждение сигнала «это баг» от xfail и не ломать CI при обычном рефакторинге из-за `strict=True`.
- **Гарантия вышестоящего / недостижимое**: по-прежнему **остаются зелёными тестами-стражами**, фиксирующими текущее поведение и сохраняющими регрессионный датчик.
  «Не исправлять код» не означает «удалить тест» — все три теста успешно конструируют реальные входные данные и проверяют код этого репозитория
  (`src/config.py` / `src/tts_service.py`); удаление потеряло бы чувствительность к будущим изменениям поведения.
  Только для #14, где аргумент «недостижимости» может перестать быть справедливым после рефакторинга `sub_agent`, добавлено укрепление кодом в одну строку (см. ниже).

## Оставлены зелёными тестами-стражами (гарантия вышестоящего / недостижимое, код не исправляется)

### Дефект #6 — отсутствие проверки при ошибочной настройке providers как dict (гарантия вышестоящего)

- Симптом: при непустом `providers` типа dict возникает `AttributeError: 'str' object has no attribute 'get'`
  (отсутствует проверка структуры при ошибочной конфигурации).
- Вердикт: `_conf_schema.json` уже требует, чтобы `providers` был массивом; при сохранении через WebUI AstrBot
  отклонит его через `validate_config()`. Сценарий возможен только при ручном редактировании `data/config/<plugin>_config.json` в обход этой защиты —
  это ответственность пользователя, а не обязательное поле для исправления в этом репозитории.
- Страж: `tests/test_config.py::TestAcceptedBehavior::test_providers_as_dict_raises_attribute_error`
  фиксирует текущее поведение «ошибочная настройка как dict вызывает `AttributeError`»; если в будущем будет добавлена проверка структуры, тест упадёт, сигнализируя об изменении поведения.

### Дефект #15 — bool проходит проверку типа context_window (гарантия вышестоящего)

- Симптом: `isinstance(x, int)` молча пропускает `True` (`bool` — подкласс `int`).
- Вердикт: входные данные приходят из конфигурации, и schema объявляет их как `int` — это зона ответственности AstrBot; путь вывода LLM,
  `validate_params`, не покрыт вышестоящей проверкой и должен сам исключать `bool` (ср. P3-3a). Конфигурационная сторона — ответственность вышестоящего компонента, код не исправляется.
- Страж: `tests/test_tts_service.py::TestAcceptedBehavior::test_bool_context_window_silently_accepted`
  фиксирует текущее поведение «`context_window: True` принимается как корректное окно и возвращает историю, а не пустоту».

## Переведены в зелёные тесты компромиссы дизайна (принятое поведение)

- **Дефект #1** (пустой / состоящий только из пробелов тег `<tts>` возвращает пустой список): у пустого тега нет содержимого для озвучивания, молчаливое удаление всей секции допустимо.
- **Дефект #3** (вложенные теги `<tts>` рекурсивно не раскрываются, внутренний текст остаётся): вложенность — неопределённые входные данные, и нерекурсивный парсер даёт
  неопределённый вывод, что допустимо.
- **Дефект #5** (исправлен): `_load_providers` ранее записывал `__resolved_name` непосредственно в `raw_config` вызывающей стороны;
  в P2⑥ (1.0.0) перешли на глубокое копирование исходной конфигурации, а внутренние приватные поля пишутся только в скопированные записи — конфигурация вызывающей стороны больше не загрязняется.
