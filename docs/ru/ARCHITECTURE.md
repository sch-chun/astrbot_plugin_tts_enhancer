## 1. Цели и позиционирование дизайна

AstrBot по умолчанию может передавать в TTS только обычный текст. Однако современные сервисы синтеза речи давно поддерживают такие богатые возможности, как теги эмоций, инструкции на естественном языке, диалекты, клонирование голоса и дизайн голоса. Позиционирование TTS Enhancer — **преодолеть разрыв между «традиционным текстовым вводом» и «богатыми возможностями провайдеров»** и подключать любые голосовые сервисы **высокомодульным способом** без изменения кода ядра.

Ключевые принципы дизайна:

- **Высокомодульная мульти-провайдерная архитектура**: каждый провайдер — независимый адаптер (Adapter), не влияющий на остальные; новый провайдер подключается по принципу «подключил и работает».
- **Механизм документов о возможностях (Capability Docs)**: к каждому провайдеру прилагается Markdown-документ, описывающий его параметры и способы использования; SubAgent на его основе динамически генерирует оптимальные параметры, «не выходящие за границы».
- **Фронтенд по требованию**: переиспользуемые компоненты закрывают типовые сценарии управления, а кастомные компоненты учитывают особенности провайдера. Официальная консоль может использоваться как основной или дополнительный сценарий; её наличие не означает, что компонент не нужен.
- **Защитные границы**: идентификаторы файлов, параметры маршрутов, расширения загружаемых файлов, обработка API Key — всё имеет явные ограничения безопасности.

## 2. Общая архитектура

Плагин занимает в конвейере событий AstrBot звено «декорирования результата» и делится на четыре слоя:

```
┌──────────────────────────────────────────────────────────────────────┐
│  Основная модель (LLM)                                                │
│  - выводит теги <tts>…</tts> (или активный вызов через Agent Tool)    │
│  - on_llm_req внедряет промпт-триггер TTS                             │
└───────────────────────────────┬──────────────────────────────────────┘
                                 │
┌───────────────────────────────▼──────────────────────────────────────┐
│  Плагин TTS Enhancer (main.py / src/*)                                 │
│  - on_decorate разбирает теги → разделяет текстовые и TTS-сегменты    │
│  - TTSService оркестрирует синтез, контекст, маршрутизацию персон,    │
│    откат между провайдерами                                            │
│  - SendVoiceTool предоставляет активный инструмент send_voice_to_user │
│  - Маршруты Web API (управление голосами/файлами, загрузка, KV)        │
└───────────────────────────────┬──────────────────────────────────────┘
                                 │
┌───────────────────────────────▼──────────────────────────────────────┐
│  TTSSubAgent (src/sub_agent.py)                                        │
│  - вызывает провайдер модели улучшения (опционально enhance_llm_provider)│
│  - внедряет документ о возможностях + персону + контекст →            │
│    формирует структурированные параметры через инструмент tts_enhance │
└───────────────────────────────┬──────────────────────────────────────┘
                                 │
┌───────────────────────────────▼──────────────────────────────────────┐
│  Provider Adapter (providers/*)                                        │
│  - валидация/очистка параметров → вызов реального TTS API →          │
│    загрузка и сохранение аудио на диск                                 │
│  - опционально: управление голосами (создание/запрос/просмотр/список/  │
│    удаление — набор зависит от провайдера), управление файлами           │
│  - автоматическое обнаружение + создане через фабрику                  │
└──────────────────────────────────────────────────────────────────────┘
```

Можно также взглянуть на полный цикл синтеза с точки зрения потока:

```mermaid
flowchart TD
    A[Основная модель выводит текст с &lt;tts&gt;] --> B[хук on_decorate]
    B --> C[tts_parser разделяет текстовые / TTS-сегменты]
    C --> D[TTSService.synthesize]
    D --> E[определение текущей персоны persona_id]
    E --> F[секционирование провайдеров: персональные + общий резерв]
    F --> G{улучшение включено и есть документ?}
    G -- нет --> H[откат на обычный текст call_api]
    G -- да --> I[SubAgent генерирует параметры tts_enhance<br/>(внутри структурная повторная попытка role:tool, ≤2)]
    I --> J{Возвращены корректные параметры?}
    J -- да (включая очистку последних некорректных) --> M[синтез call_api]
    J -- нет (исключения инструмента исчерпаны) --> Q[откат на синтез обычного текста (оригинал + пустые параметры)]
    Q --> M
    H --> M
    M --> N[аудиосообщение Record]
    N --> O[возврат цепочки сообщений]
```

## 3. Жизненный цикл запроса (от начала до конца)

Существуют два пути активации, которые в итоге сходятся в `TTSService.synthesize()`.

### 3.1 Путь активации через тег (по умолчанию)

1. **`on_llm_req`**: если настроен провайдер и задан `tts_prompt`, промпт-триггер добавляется в системный промпт, побуждая основную модель оборачивать текст для синтеза в теги `<tts>…</tts>`.
2. **`on_decorate`** (`priority=13`): сканирует текстовые компоненты `Plain` в цепочке сообщений; при обнаружении тега `<tts>`:
   - вызывает `tts_service.get_context_messages(event)` для получения последних `context_window` витков контекста;
   - для текста с тегом вызывает `_process_tts_text()` и обрабатывает его по сегментам;
   - с помощью `split_by_tts_tags()` разделяет текст на сегменты `text` и `tts`; текстовые остаются `Plain`, TTS-сегменты передаются в `synthesize()`;
   - при успехе возвращается компонент `Record` (опционально с `dual_output` сохраняется и оригинальный текст), при неудаче — откат на `Plain`-текст.

### 3.2 Путь активации через инструмент (Agent Loop)

1. Плагин в `__init__` регистрирует инструмент `send_voice_to_user` через `context.add_llm_tools(SendVoiceTool(...))` (определён в `src/tools.py`).
2. Модель в цикле Agent активно вызывает этот инструмент, передавая `text` (и опционально `session`).
3. Внутри инструмент получает контекст, вызывает `tts_service.synthesize()` и отправляет аудиосообщение в целевую сессию через `star_context.send_message()`.

Оба пути используют один и тот же экземпляр `TTSService` (создаётся в `main.py`, получает `context / providers / config / audio_data_dir`).

## 4. Разбор ключевых модулей

### 4.1 `main.py` — точка входа плагина

Ответственность: инициализация, хуки событий, маршруты Web API, проверки безопасности.

- **`TTSEnhancerPlugin(Star)`**: точка входа жизненного цикла. Инициализирует каталог данных (`plugin_data/<name>/{uploads,audio}`), создаёт `TTSService`, регистрирует `SendVoiceTool`, регистрирует все веб-маршруты.
- **Хуки событий**:
  - `on_llm_req`: внедряет TTS-промпт.
  - `on_decorate`: разбирает и заменяет теги `<tts>`.
- **Web API** (все под префиксом `/<plugin_name>/`, см. раздел 10 по безопасности):
  - `GET /providers`: возвращает список провайдеров, сгруппированный по `template_key`, с маскированным `api_key`. Для каждой группы также возвращаются:
    - `display_name` — отображаемое имя из `DISPLAY_NAME` адаптера (при отсутствии — `template_key`);
    - `capabilities.voice_management` — поддерживает ли адаптер управление голосами; фронтенд использует этот флаг для видимости вкладки, но он не означает наличия всех операций;
    - `ui_component` — имя соответствующего фронтенд-компонента по соглашению с `template_key`.
  - `POST /voice/create`, `POST /voice/query`, `POST /voice/list`, `POST /voice/delete`: управление голосами, маршрутизация по `entry_id` к адаптеру. `POST /voice/query` запрашивает статус голоса; наличие маршрута не гарантирует реализацию `query_voice()` у каждого провайдера.
  - `POST /upload`: локальная загрузка аудио (whitelist расширений).
  - `POST /voice/preview`: превью голоса (возврат Base64).
  - `POST /kv/{set,get,delete}`: универсальное KV-хранилище (фронтенд/адаптеры сохраняют метаданные).
  - `POST /file/{upload,list,get,delete}`: управление файлами провайдера (транслирует `**kwargs`).
- **Вспомогательные функции безопасности**: `_SAFE_FILE_ID_RE`, `_validate_file_id()`, `_resolve_uploads_path()` (сравнение родительского каталога после resolve для защиты от обхода), `_parse_entry_id()` (проверка типа и границ, исключает `bool`).

### 4.2 `src/config.py` — управление конфигурацией

`TTSEnhancerConfig` отвечает за загрузку и нормализацию конфигурации:

- `_load_providers()`: стабильная сортировка по `priority` (меньше значение — выше приоритет); обнаруживает дубли `priority` и совпадения `display_name` (при совпадении автоматически добавляются суффиксы `#2`, `#3` и записываются в приватное поле `__resolved_name`).
- `get_providers()`: возвращает отсортированный список провайдеров.
- `get_entry_name(entry, index)`: определение отображаемого имени (приоритет: `__resolved_name` → `display_name` → `template_key (voice)` → `template_key #index` → `template_key`).
- `get(key, default)`: чтение параметра верхнего уровня; `has_providers()`: есть ли провайдеры.
- `_to_priority_int()`: нечисловое `priority` заменяется на `100` с предупреждением, чтобы избежать `TypeError` при смешанной сортировке `int/str`.

### 4.3 `src/tts_parser.py` — разбор тегов

`split_by_tts_tags(text)` разделяет текст с `<tts>…</tts>` на список `{type: 'text'|'tts', content}`:

- нестроковый аргумент сразу возвращает пустой список (обрабатывается как «нет содержимого», а не как исключение).
- обрабатывает одиночные закрывающие теги, вложенность/отсутствие пар; содержимое тега очищается от граничных разделителей и пробелов.
- если совсем нет валидных фрагментов, после удаления тегов возвращается как обычный текст (откат).
- константа граничного разделителя: `BOUNDARY_SEPARATORS = "$"` (используется для очистки остатков на границах тегов).

### 4.4 `src/tts_service.py` — оркестрация синтеза

`TTSService` — «главный дирижёр» процесса синтеза:

- `get_context_messages(event)`: берёт из `conversation_manager` последние `context_window` сообщений **user** как окно (подсчёт по user), собирает в обратном порядке, затем восстанавливает хронологический порядок; любое исключение — откат на пустой список.
- `get_current_persona(event)`: определяет персону, действующую в текущей сессии, возвращает `(prompt, persona_id)`; если `conversation_manager` / `persona_manager` не готовы — откат на пустые значения.
- `synthesize(raw_text, event, context_messages)` (ядро):
  1. Определение персоны → разделение провайдеров на **персональные** (совпадает `persona_id`) и **общие резервные** (без `persona_id`), упорядоченный перебор (персональные первыми).
  2. Если кандидатов нет — только Warning, без тихого завершения.
  3. Для каждой записи: внедрение `_data_dir` → `ProviderFactory.get_adapter()` → определение `enable_enhance = config.enable_enhance and bool(docs_content)`.
  4. **Без улучшения/без документа**: сразу обычный синтез с `raw_params={}` (чтобы не вызывать LLM впустую).
    5. **Путь с улучшением**: через `adapter.get_tool_schema()` создаётся `ToolSet` → вызывается `sub_agent.call()` (внутри `max_attempts=2`):
       - возвращённая структура проверяется `adapter.validate_params()`; при неудаче проверки или исключении инструмента создаётся `[assistant(tool_calls), tool(tool_call_id, content)]` — структурированный результат инструмента с `role:"tool"` (включая текст ошибки), который через `provider.text_chat(tool_calls_result=...)` возвращается LLM для повторной попытки;
       - при неудаче последней проверки, если адаптер поддерживает очистку, `sub_agent.call()` возвращает параметры после `sanitize_params()`; при исчерпании исключений инструмента возвращается `None`, и `tts_service` откатывается на обычный синтез (оригинал + пустые параметры); переход к следующему провайдеру происходит только если и этот обычный синтез не удался.
  6. Если SubAgent вернул пустой `text`, сохраняется оригинал; при успехе `call_api()` возвращает `Record.fromFileSystem(path, text=...)`, при неудаче — переход к следующему провайдеру.

### 4.5 `src/sub_agent.py` — SubAgent

`TTSSubAgent.call(...)` вызывает LLM для генерации структурированных TTS-параметров:

- Определение модели улучшения: если задан `enhance_llm_provider`, берётся по ID, иначе используется провайдер текущей сессии; если не удалось получить — ошибка и возврат `None`.
- Формирование пользовательского промпта: персона + краткий контекст + текст для синтеза.
- Вызов `provider.text_chat(..., func_tool=tool_set)`; приоритет отдаётся разбору `tools_call_args` с `tools_call_name == 'tts_enhance'`;
- при отсутствии вызова инструмента — откат на извлечение из `completion_text` (только `text`); итоговая неудача — возврат `None`.
- Механизм повторных попыток: при неудаче проверки или исключении инструмента создаётся `[assistant(tool_calls), tool(tool_call_id, content)]` и структурированно возвращается через `tool_calls_result` (настоящий цикл на уровне объектов с `role:"tool"`), а не «сплющивается» в промпт; только если модель не инициировала вызов инструмента, ей отправляется лёгкое напоминание с `role:"user"` вызвать его снова.
- Все исключения перехватываются и логируются, никогда не пробрасываются вверх.

### 4.6 `src/tools.py` — активный голосовой инструмент

`SendVoiceTool(FunctionTool)` предоставляет `send_voice_to_user`:

- Параметры: `text` (обязательный), `session` (опциональный, формат `platform_id:message_type:session_id`).
- `__post_init__` проверяет, что `tts_service` не пустой; в `call()` получается контекст, вызывается `synthesize()` и отправка через `star_context.send_message()`.

## 5. Система адаптеров провайдеров

### 5.1 Контракт интерфейса абстрактного базового класса (`providers/base.py`)

`TTSProviderAdapter(ABC)` определяет интерфейсы, которые все адаптеры должны / могут реализовать:

**Абстрактные методы (обязательны):**

| Метод | Описание |
|-------|----------|
| `get_subagent_system_prompt() -> str` | формирует системный промпт, внедряемый в SubAgent (обычно с присоединением документа о возможностях). |
| `get_tool_schema() -> FunctionTool \| None` | через базовый `build_enhance_tool` возвращает инструмент `tts_enhance` (с уже подключённым обработчиком проверки); если Function Calling не поддерживается, можно вернуть `None`. |
| `call_api(text, raw_params, config, voice_id=None) -> str` | выполняет синтез и возвращает путь к аудиофайлу (или пустую строку при неудаче). `voice_id` используется для явного переопределения голоса при превью. |

**Опциональные возможности (по умолчанию `raise NotImplementedError`):**

- Управление голосами: `create_voice(params)`, `query_voice(voice_id, custom_speaker_id=None)`, `list_voice(**kwargs)`, `delete_voice(**kwargs)`. Реализуются только нужные провайдеру методы; например, Seed TTS 3.0 поддерживает `create_voice` и `query_voice`, но не список и удаление. Превью использует общий маршрут `/voice/preview`.
- Управление файлами: `upload_file(...)`, `list_files(**kwargs)`, `get_file_content(file_id)`, `delete_file(file_id, **kwargs)`.

**Общие утилиты (уже реализованы в базовом классе, можно использовать напрямую):**

- Безопасное приведение типов: `_as_float(value)`, `_as_int(value)` (совместимо с числами, возвращаемыми LLM как строки, исключает `bool`).
- Проверка: `validate_voice_id(...)` (длина 8–256, первый символ, набор символов, ограничение последнего символа), `_count_text_chars(text)` (CJK/полноширинные/emoji считаются за 2), `validate_text_length(...)` (на основе указанного подсчёта).
- Обработка параметров: `validate_params(params) -> (bool, str)`, `sanitize_params(params) -> dict` (переопределяются в подклассах для конкретных диапазонов/перечислений).

**Документы и метаданные:**

- `DOCS_KEY` (атрибут класса, опционально): явно задаёт, какой документ о возможностях использовать; по умолчанию — откат на `template_key`.
- Свойство `docs_key`, метод `_load_docs()`: читает документ из `providers/docs/<docs_key>.md`.
- `get_docs_for_voice(voice)`: может динамически выбирать документ по ID голоса (например, `*_design.md` для дизайн-голосов).

### 5.2 Автоматическое обнаружение и фабрика (`providers/__init__.py`)

`ProviderFactory` реализует «плагинизацию без конфигурации»:

- `_discover_adapters()`: сканирует `providers/*.py`, **пропуская файлы с ведущим подчёркиванием и `base.py`**; динамически импортирует через `importlib`; собирает конкретные классы, для которых `issubclass(obj, TTSProviderAdapter)` и `obj.__module__ == module.__name__` (последнее защищает от ошибочной регистрации базового класса под чужим именем модуля при множественном наследовании).
- `get_adapter(entry)`: `entry["__template_key"]` — это имя файла модуля (без `.py`), используется как ключ сопоставления; результат кэшируется по классу.

> `__template_key` автоматически внедряется фреймворком AstrBot в конфигурации `template_list`; имя файла и ключ `templates` в schema должны совпадать.

### 5.3 Общий базовый класс `BailianSpeechSynthesizerAdapter`

База, общая для адаптеров семейства Bailian (`providers/_bailian_speech_synthesizer.py`, ведущее подчёркивание предотвращает автоматическое обнаружение):

- Инкапсулирует endpoint SpeechSynthesizer Alibaba Cloud Bailian, Bearer-аутентификацию, обработку запросов/ответов и загрузку аудио.
- Управляется `MODEL_NAME` (например, `qwen-audio-3.0-tts`, `cosyvoice-v3.5`) и `VALID_LANGS`; подклассам достаточно объявить эти два и несколько отличий для подключения.
- Реализует `get_tool_schema()` (`tts_enhance`: text/instruction/volume/rate/pitch/language_hints), `get_subagent_system_prompt()`, `call_api()`, `validate_params/sanitize_params`, `create_voice` (ветви клонирования/дизайна), `list_voice`, `delete_voice`.
- `_extract_model_from_voice_id()`: определяет `flash/plus` из ID клонированного голоса, решая проблему автоматического подбора версии модели.
- При инициализации маскирует `api_key` в `entry`, чтобы не попадал в debug-логи, и проверяет конфликт между `model` и значением, извлечённым из ID голоса.

Конкретные адаптеры Bailian (например, `bailian_qwen_audio_3_0_tts.py`) часто состоят из нескольких строк, объявляя только отличия вроде `MODEL_NAME`.

### 5.4 Общий базовый класс `FishAudioAdapter`

Общая база адаптеров Fish Audio (`providers/_fish_audio.py`, ведущее подчёркивание предотвращает автоматическое обнаружение):

- Инкапсулирует `POST https://api.fish.audio/v1/tts`, Bearer-аутентификацию и заголовок запроса `model`.
- Централизует проверку/очистку параметров, прокси, поля текста и языка, скорость/громкость в `prosody`, формат аудио и битрейт/частоту дискретизации, параметры сэмплинга/чанков, ссылки на словарь произношения, обработку ошибок и сохранение аудио.
- `_resolve_model()`: непустой `MODEL_NAME` в подклассе сразу возвращает фиксированную модель; S2 выбирает `s2.1-pro`, `s2.1-pro-free` или `s2-pro` из конфигурации.
- `_resolve_reference_id()`: `voice_id` при превью имеет приоритет; иначе используется единственный настроенный `reference_id`.
- `FishAudioS2Adapter` сохраняет схему инструмента и документ возможностей S2. `FishAudioDrama3Adapter` фиксирует `MODEL_NAME = "drama-3"`, отключает `normalize_loudness` (только для семейства S2) и предоставляет отдельную схему инструмента режиссёрских указаний и документ возможностей.

### 5.5 Volcengine Seed TTS 3.0 (`VolcengineSeedTts30Adapter`)

- Ключ провайдера — `volcengine_seed_tts_3_0`, отображаемое имя — `Seed TTS 3.0`.
- Синтез выполняется через `POST /api/v3/text-to-speech/{voice_id}/streaming` с аутентификацией заголовком `X-Api-Key`.
- Ответ передаётся как поток JSONL. Адаптер накапливает события и сохраняет аудио **только после получения корректного финального события и непустых аудиоданных**; незавершённый или ошибочный поток не считается успешной синтезой.
- Специфичные поля инструмента: `instructions` — указания по выразительности, эмоциям или диалекту; `language_code` — необязательный код языка или диалекта, передаваемый только SubAgent (`auto` или один из 119 официальных кодов), без значения по умолчанию в конфигурации провайдера. Пример структурированных параметров:

  ```json
  {
    "text": "Сегодня хорошая погода.",
    "instructions": ["Спокойно, с лёгкой улыбкой"],
    "language_code": "ru"
  }
  ```

- Управление голосами включает `create_voice` и `query_voice`; превью выполняется через общий маршрут `/voice/preview`. Операции получения списка и удаления отсутствуют.
- Существующий ID голоса повторно использует слот в аккаунте. Пользовательский ID голоса относится к слоту с оплатой после использования; плата за слот взимается при первом официальном синтезе.
- Фронтенд использует отдельный компонент `volcengine_seed_tts_3_0.js` для ручного клонирования, запроса статуса одного голоса, превью, пояснения тарификации слотов и переходов к официальным ресурсам. Дизайн голосов открывается в [официальной консоли](https://console.volcengine.com/speech/new/experience/timbre), а список доступных голосов — в [официальной документации](https://docs.volcengine.com/docs/doubao-voice/voice-list-3-0-1).
- Список приобретённых слотов Mega намеренно не интегрирован: соответствующие API используют другой способ аутентификации OpenAPI (AK/SK).

### 5.6 Механизм документов о возможностях

«Документ о возможностях» — основа интеллектуальной генерации параметров SubAgent, хранится в `providers/docs/<docs_key>.md`:

- Содержимое должно покрывать: таблицу ключевых параметров (тип/диапазон/значение по умолчанию), перечисления тегов эмоций/диалектов/языков, примеры использования.
- **Ключевой раздел `## 你的任务`**: говорит SubAgent, как выбирать параметры на основе контекста и как вызывать `tts_enhance`.
- Дизайн-голоса (не поддерживают диалекты) описываются отдельно в `<docs_key>_design.md`; `get_docs_for_voice()` автоматически переключается по ID голоса.
- Провайдеры с одной моделью могут переиспользовать один документ через `DOCS_KEY` в подклассе (например, Bailian-версия MiniMax переиспользует официальный документ MiniMax), избегая избыточного копирования.

## 6. Откат между провайдерами и маршрутизация персон

Стратегия выбора провайдера в `TTSService.synthesize()`:

1. **Секционирование по персоне**: по текущему `persona_id` провайдеры делятся на `bound` (привязанные к этой персоне) и `unbound` (не привязанные), перебор упорядочен, `bound` идут первыми.
2. **Семантика отката**: если все `bound` не удались и есть `unbound`, после Warning происходит откат на общий голос; если нет доступных голосов вовсе или персональные не удались и резерва нет — Warning и отказ от этого синтеза (возврат `None`).
3. **Внутренние повторные попытки одного провайдера**: при некорректных параметрах SubAgent или исключении инструмента структурированный результат с `role:"tool"` возвращается LLM для повторной попытки (встроено не более 2); при неудаче последней проверки — очистка через `sanitize_params`; при исчерпании исключений инструмента — откат на обычный синтез (оригинал); переход к следующему провайдеру только если и эта попытка не удалась.
4. **Откат на обычный текст**: провайдеры без включённого улучшения или без документа сразу синтезируют обычный текст, минуя SubAgent.

## 7. Механизм улучшения через SubAgent

Надёжность процесса улучшения:

- **Структурированный вывод**: через Function Calling `tts_enhance` модель выводит объект параметров, а не свободный текст. Набор полей определяется адаптером: например, Seed TTS 3.0 использует `text`, `instructions`, `language_code` (и при необходимости `speed`/`volume`/`pitch`), а не общий для всех провайдеров `instruction`/`language_hints`.
- **Двухэтапная проверка**: сначала `validate_params` (диапазоны/перечисления) → при последней неудаче `sanitize_params` (отбросить некорректные, сохранить корректные).
- **Учёт контекста**: последние сообщения диалога и промпт `persona` внедряются в SubAgent, чтобы суждения об эмоции/скорости/языке соответствовали контексту.
- **Цепочка откатов**: неудача вызова инструмента → откат на разбор текста → возврат `None` → основной поток переключает провайдера или обычный текст.
- **Нет документа — значит обычный текст**: гарантирует, что «провайдер без документа» не будет зря вызывать LLM.

## 8. Архитектура фронтенда (`pages/tts_studio/`)

Фронтенд — приложение Vue 3, **не требующее сборки**:

- `index.html` подключает через `<script>` локальный `static/vue.global.prod.js` (UMD, работает офлайн, без зависимостей от CDN), `app.js` загружается как `type="module"`.
- `app.js`:
  - `bridge = window.AstrBotPluginPage`, все вызовы бэкенда идут через `bridge` (включая `bridge.ready()`, `bridge.apiGet('providers')`, `bridge.upload`), что обходит аутентификацию `asset_token` и кросс-доменные ограничения Pages.
  - `display_name`, `capabilities` и `ui_component` берутся из ответа `GET /providers`. Отображаемое имя определяет бэкенд через `DISPLAY_NAME` адаптера, а видимость вкладки управления голосами — флаг `capabilities.voice_management`.
  - `componentMap`: сопоставляет `template_key` / `ui_component` соответствующему Vue-компоненту. Кастомный UI регистрируется здесь; отдельная фронтенд-таблица отображаемых имён не используется.
  - Рендерит Tabs, сгруппированные по `template_key`; текущий компонент динамически загружается через `<component :is>` и получает `entries / bridge / template-key`.
- **Организация компонентов**:
  - `components/common/`: компоненты, общие для провайдеров (`bailian_speech_synthesizer.js` — режимы клонирования/дизайна (аудио клонирования кодируется в браузере как Data URL и отправляется), `voice_preview_modal.js` — модальное окно превью, `delete_confirm_modal.js` — подтверждение удаления).
  - `components/*.js`: обёртки для переиспользуемых сценариев либо кастомные компоненты провайдеров. Например, `volcengine_seed_tts_3_0.js` реализует создание, запрос и превью голоса, пояснения тарификации и ссылки на официальные ресурсы; он не сводится к внешней ссылке на консоль.
  - `composables/`: `useAudioManager` (глобальный синглтон аудио/громкость), `useTextValidator` (подсчёт и проверка: иероглиф = 2 символа), `useClipboard`, `useToast`.
- Стили собраны в `style.css`; у фронтенда нет шага сборки или конфигурации ESLint, поэтому npm-инструментарий не требуется.
- **Настраиваемый фон**: страница управления поддерживает загрузку одного фонового изображения через параметр `page_background` (тип file); маршрут бэкенда `/<plugin>/page-background` читает изображение и возвращает его как base64 Data URL (чтобы не передавать бинарные данные через bridge и избежать кросс-доменных/внешних ссылок); фронтенд `applyPageBackground()` рендерит слой `#page-bg` с фиксированным фоном только если `data_url` не пуст, применяя прозрачность и размытие по `page_background_opacity` / `page_background_blur`. Карточки контента и поля форм стали полупрозрачными «матовыми», чтобы фон просвечивал.
- **Архитектура наложений (модальные окна / Toast / полоса громкости)**: глобальная полоса громкости, все модальные оверлеи и toast-уведомления монтируются через `<Teleport to="body">` в body (fixed + `100vw/100vh`). Анимация появления страницы использует `animation-fill-mode: both`, после завершения оставляя на родительском элементе два типа стойких побочных эффекта — compositor-трансформацию (вычисленный transform — единичная матрица вместо `none`, становящаяся содержащим блоком для потомков `position: fixed`) и compositor-слой (т.е. контекст наложения, жёстко фиксирующий z-index в поддереве); Teleport в body устойчив к обоим эффектам, и новым наложениям следует следовать этой архитектуре.
- **Соглашение по анимациям**: одноразовые появление/исчезновение (модальные окна, вход страницы/вкладок) — всегда `<Transition>` — классы анимации снимаются после проигрывания, без остатка; непрерывные переходы (полоса подсветки вкладки) — compositor-анимация transform + `will-change`, чтобы избежать послойной вёрстки каждый кадр. Всё отключается при `@media (prefers-reduced-motion: reduce)`.

> Компромисс дизайна: закрывать отсутствие UI там, где провайдер предоставляет только API, и не дублировать официальную консоль без необходимости. Если особенности провайдера требуют иного сценария (как у Seed TTS 3.0), добавляется кастомный компонент с необходимыми ссылками на официальные ресурсы.

## 9. Система конфигурации (`_conf_schema.json`)

Параметры верхнего уровня:

| Параметр | Тип | По умолчанию | Описание |
|----------|-----|--------------|----------|
| `enable_enhance` | bool | true | включить улучшение параметров через SubAgent |
| `enhance_llm_provider` | string (`select_provider`) | "" | модель улучшения; пусто = модель текущей сессии |
| `context_window` | int | 10 | окно контекста SubAgent (по числу сообщений user) |
| `dual_output` | bool | false | выводить и текст, и голос одновременно |
| `tts_prompt` | text | промпт-триггер | описание триггера TTS, внедряемое в основную модель |
| `page_background` | file | [] | фоновое изображение страницы управления (пусто = не показывать) |
| `page_background_opacity` | float | 0.5 | прозрачность фона (0~1, применяется только при заданном изображении) |
| `page_background_blur` | int | 0 | размытие фона (0~30px, применяется только при заданном изображении) |
| `providers` | `template_list` | — | список провайдеров (поддерживает несколько записей с откатом) |

`providers` — это `template_list`: каждый шаблон содержит `name`/`hint`/`display_item`/`items`. В `items` поддерживаются `_special` (`select_provider`/`select_persona`), `secret: true` (маска поля пароля), `options`, `condition` (условное отображение по значениям других полей, например MiMo переключает поля голоса/дизайна/клонирования по `model`). Фреймворк внедряет `__template_key` для каждой записи.

## 10. Безопасность

- **Whitelist идентификаторов файлов**: `_SAFE_FILE_ID_RE = ^[A-Za-z0-9_][A-Za-z0-9_.\-]{0,127}$`, первый символ ограничен, исключая `.`/`..`/`.env` и т.п.; точка разрешена (реальные имена файлов вроде `upload_<ts>.mp3`), но `/` и `\` всегда исключены.
- **Вторая линия защиты от обхода пути**: `_resolve_uploads_path()` после `Path.resolve()` сравнивает родительский каталог, гарантируя, что результат не выходит за пределы `uploads`.
- **Проверка параметров маршрута**: `_parse_entry_id()` проверяет тип (исключает `bool`) и границы, при некорректном значении возвращает `None` → 404.
- **Whitelist расширений загрузки**: `upload_file` разрешает только `wav/mp3/m4a/aac/ogg/flac`, файлы с иным расширением не сохраняются.
- **Маскировка API Key**: `/providers` и инициализация адаптеров маскируют `api_key` как `***** + последние 5 символов`, чтобы не утечёл в логи.
- **Способ отправки аудио**: аудио для клонирования голоса кодируется страницей управления в браузере как Data URL (Base64) и отправляется напрямую в API создания, без публичного адреса или внутреннего порта прослушивания.

## 11. Каталог данных и сохранение

Корень данных плагина: `get_astrbot_data_path() / "plugin_data" / <plugin_name>`, внутри:

- `uploads/`: загруженные пользователем референсные/клонированные аудио (`upload_<метка_времени_в_мс>.<ext>`).
- `audio/`: результаты синтеза (`tts_<метка_времени>.<fmt>`), внедряются в адаптер через `_data_dir`.
- `cache/mimo_voiceclone/`: кэш Base64-предкодирования аудио-образцов для клонирования MiMo (ключ включает mtime/size, при изменении автоматически инвалидируется).

KV-хранилище (`/kv/*`) предоставляется фреймворком AstrBot, фронтенд/адаптеры используют его для метаданных (например, список неактивных голосов MiniMax `bailian_minimax_unactivated_list`, `prompt_text` для клонирования и т.д.).

> **Принцип сохранения**: все рабочие данные плагина пишутся в `plugin_data/`, а не в каталог самого плагина (чтобы не потерять их при обновлении/переустановке).
