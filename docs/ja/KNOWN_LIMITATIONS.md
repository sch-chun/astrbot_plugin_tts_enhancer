# 既知の制限と上流の責任

本ファイルは、复核の結果「設計上の取舍 / 上流保証 / 到達不能」と判定され、本プラグインが主体的に修正しない（または極小な補強のみ行う）挙動を記録します。

対応するテストは元々 `@pytest.mark.xfail(strict=True)` で固化されていましたが、2 次复核で性質ごとに拆分処理されました：

- **設計取舍类**：「受け入れた実際の挙動」をアサートする普通のグリーンテストへ変換（命名から `should_not` の缺陷示唆を外す）、
  現在の契約をロックし、xfail が「これはバグだ」という誤解を発し続けるのを防ぐとともに、`strict=True` が通常のリファクタリング時に CI を誤って落とすのも防ぎます。
- **上流保証 / 不可達类**：引き続き**グリーンテストガードとして保持**し、現在の挙動をロックして回帰センチネルを残します。
  「コードを直さない」ことは「テストを消す」ことではありません——3 つのケースはいずれも実際の入力を構築し、本リポジトリのコード
  （`src/config.py` / `src/tts_service.py`）をテストしています。削除すれば将来の挙動変更を検知する能力を失います。
  #14 のみ、「不可達」の論拠が `sub_agent` のリファクタリング後には有効とは限らないため、追加で 1 行のコード補強を行いました（下記参照）。

## グリーンテストガードとして保持（上流保証 / 不可達、コードは修正しない）

### 缺陷#6 — providers が dict として誤設定された場合の検証欠如（上流保証）

- 現象：`providers` が空でない dict のとき、`AttributeError: 'str' object has no attribute 'get'` が発生します
  （設定構造の誤設定に対する構造検証の欠如）。
- 判定：`_conf_schema.json` は `providers` を配列として要求しており、WebUI で保存すれば AstrBot の
  `validate_config()` が拒否します；手動で `data/config/<plugin>_config.json` を編集して防壁を迂回した場合にのみ発生し得るため、
  利用者の責任であり本リポジトリの必須修正項目ではありません。
- ガード：`tests/test_config.py::TestAcceptedBehavior::test_providers_as_dict_raises_attribute_error` が
  「dict への誤設定が `AttributeError` を引き起こす」という現在の挙動をロックします。将来構造検証を追加した場合は失敗し、挙動変更を通知します。

### 缺陷#15 — bool が context_window の型チェックを通過（上流保証）

- 現象：`isinstance(x, int)` は `True` に対して黙って通過します（`bool` は `int` のサブクラス）。
- 判定：この入力は設定に由来し、スキーマも `int` を宣言しているため AstrBot の検証範囲に属します；LLM 出力経路の
  `validate_params` は上流に覆われないため、自ら `bool` を除外すべきです（P3-3a に対照）。設定側は上流の責任であり、コードは修正しません。
- ガード：`tests/test_tts_service.py::TestAcceptedBehavior::test_bool_context_window_silently_accepted` が
  「`context_window: True` が正当なウィンドウとして扱われ、空ではなく履歴を返す」という現在の挙動をロックします。

## グリーンテストへ転換した設計取舍（受け入れた挙動）

- **缺陷#1**（空 / 空白のみの `<tts>` タグが空リストを返す）：空タグには読み上げる内容がなく、セグメント全体が黙って削除されても受け入れられます。
- **缺陷#3**（ネストした `<tts>` タグが再帰的に展開されず、内側が残る）：ネストは未定義の入力であり、非再帰的なパーサーが
  未定義の出力を出しても受け入れられます。
- **缺陷#5**（修正済み）：`_load_providers` は以前、呼び出し元の `raw_config` に `__resolved_name` をその場で書き込んでいました；
  P2⑥（1.0.0）で元の設定をディープコピーする方式に変更し、内部のプライベートフィールドはコピー後のエントリにのみ書き込むようにしたため、呼び出し元の設定が汚染されなくなりました。
